# 문서 운영 — libmarks

## 1. 목적별 기준 문서

같은 상태·정책·작업 순서를 여러 문서에서 따로 관리하지 않는다. 다른 문서에는 원문 링크와 인계에 필요한 짧은 요약만 둔다.

| 질문 | 기준 문서 | 적는 내용 | 적지 않는 내용 |
| --- | --- | --- | --- |
| 다른 PC에서 무슨 일이 있었고 지금 무엇을 주의해야 하나? | [인수인계 메모](../개발산출물/인수인계_메모.md) | 확인 시점·PC·브랜치/커밋·운영 리비전, 현재 작업 파일·담당·중단/대기 이유, 최근 결정과 근거 링크 | 전체 로드맵, 미래 기능 명세, 끝난 작업 전문, 상시 설정 명령 |
| 무엇을 어떤 순서로 해야 하나? | [상용 서비스 계획](../계획/상용_서비스_계획.md) | 작업 ID·우선순위·선행·대기 목록·검수 관문, 완료 기록의 링크 | DTO·SQL·상태 코드 전문, 실행 로그, 세션별 재개 프롬프트 |
| 어떤 동작과 제약을 만족해야 하나? | 요구사항/기능 명세 문서 | 제품 동작·권한·공개 범위·데이터/API 경계·수용 기준, 적용 범위가 명확한 결정 | 현재 진행률·다음 순서·운영 배포 상태 |
| 이번에 고칠 계약과 파일은 무엇인가? | `개발산출물/명세/<step ID>_구현명세.md` | 실제 코드 근거, 변경 파일·DTO·필드·오류·상태·검증 조건·화면 배치 | 먼 미래 작업의 구현 전문 |
| 착수한 작업을 어디서 이어 하나? | `개발산출물/진행_<작업>.md` | 목표·입력·승인 범위·담당/충돌 파일, 단계별 상태·명령·결과·다음 행동·재개 지시 | 미착수 대기 목록 전체, 제품 정책의 별도 사본 |
| 무엇을 실제 확인했나? | `개발산출물/결과/<작업>.md` | 대상 커밋·환경·명령·실제 결과·미실행·결함·근거·증거 한계 | 계획을 실행한 것처럼 적은 예상 결과 |
| 어떻게 개발·배포하나? | 개발·운영 안내, `docs/rules/` | 반복 명령·PC별 주의·개발 패턴 | 현재 실행 결과·전체 일정 |
| 과거에 무엇을 했나? | `개발산출물/완료/`, git | 완료 진행 파일·정비 전 원문·과거 결정 근거 | 새 작업을 시작하라는 현재 지시 |

기존 명세와 새 명세가 겹치면 새 명세가 **명시한 변경 범위만** 적용한다.

## 2. 갱신 순서와 문서 수명

1. 사용자 결정이 생기면 제품 동작·정책은 해당 명세에, 우선순위·선행은 계획에 기록한다. 인수인계에는 날짜·변경 요지·원문 링크만 남긴다. 확인하지 않은 사실은 “미확인”으로 적는다.
2. 작업을 착수할 때 진행 파일을 만든다. 준비·조사도 착수에 포함하며 실행 미착수/사람 대기와 구별한다. 단순 대기 후보는 계획에만 둔다. 인수인계의 작업 파일 목록은 실제 루트 `진행_*.md` 목록과 맞춘다.
3. 실행·검증 후 진행 파일에 현재 단계와 다음 행동을 갱신하고, 상세 증거는 결과 파일에 남긴다. 계획에는 단계 상태와 결과 링크만 반영한다.
4. 작업이 끝나면 진행 파일을 `완료/`로 옮긴다. 남은 범위는 계획의 기존 ID나 대기 목록에 연결한다. 기능 결함·미검증을 “나중에”라는 인수인계 목록으로 숨기지 않는다.
5. 인수인계에는 다른 PC가 오판할 현재 차이만 남긴다. 과거 PR 목록·긴 결정 전문은 결과/완료 문서로 연결한다. 실제 재개 지시는 해당 진행 파일 한 곳에서 유지한다.
6. 활성 진행·규칙·안내의 참조는 현재 기준으로 유지한다.

## 3. 완료를 판정하는 방법

| 구분 | 필요한 증거 |
| --- | --- |
| 구현 | 대상 커밋/PR과 실제 동작 코드. PR 작성·머지·CI 성공 여부를 구별 |
| 화면 연결 | 사용자 진입 경로, 필요한 역할/데이터, 행동 후 확인 가능한 결과 |
| 통합 검증 | 실제 서버·격리 DB를 연결한 사용자 여정과 실패·소유권·지연 응답 검증. 가짜 API 화면 E2E는 별도 표시 |
| 운영 확인 | 배포 리비전·시각·확인 환경과 결과. 로컬/CI 통과·머지를 배포로 간주하지 않음 |

기능별로 네 구분을 각각 기록한다. 해당하지 않으면 이유와 함께 N/A, 실행하지 못했으면 미검증/차단으로 적는다. 문서 전용 작업에는 링크·내용 보존·인코딩·diff 검증을 적용한다.

## 4. 명세 작성과 작업 착수

먼 미래 기능 전체의 세부 명세를 미리 작성하지 않는다. 기존 기능을 실제 검수한 결과를 바탕으로 바로 다음 구현 단위의 명세를 확정한다. 명세 분량보다 구현 중 임의 결정하면 안 되는 계약·실패 조건이 빠짐없이 정해졌는지로 판단한다.

| 작업 성격 | 착수 전에 정할 내용 | 실행 방식 |
| --- | --- | --- |
| 기존 기능 조사·검수 | 진행 파일의 대상·사용자 여정·권한·판정 기준·환경·증거 기록 방식 | 별도 장문 구현 명세 없이 조사·실행·검증 결과를 기록 |
| 재현된 결함 수정 | 원인·영향·변경 파일·방어 조건·회귀 검증을 짧은 수정 명세로 고정 | 진행 파일의 명세 절 또는 별도 구현 명세를 사용. 협업 구현자는 기존 역할별 명세 요구를 유지 |
| 신규 API·DB·공개/사용자 데이터 기능 | 요청/응답 전 필드·상태/오류·권한/소유권·공개 범위·트랜잭션·삭제/철회·검증 조건 | 실제 코드와 대조한 상세 구현 명세 후 구현 |
| 화면 개편/신규 개발 | 진입 동선·로딩/빈/성공/실패·권한별 동작·배치 약속·반응형/접근성·검증 기준 | 요구사항·서버 계약을 대조한 화면 명세 후 구현. Step별 배정 기준(아래 §4.1)을 적용 |

### 4.1 대기능(Feature) 단위의 Step 개수 가이드라인 (최우선 규칙)

- **최우선 원칙:** 상용 계획 상의 대기능(Feature) 단위의 Step 수는 **3개 이하 권장(적을수록 좋다)**이며, **최대 4개**로 엄격히 제한한다.
- **4개 초과 시 조치:**
  1. 사소한 단편(단순 DTO, 단일 폼 등)을 인접 Step과 병합(통합)하여 3개 이하로 압축한다.
  2. 축소 통합이 불가능할 정도로 작업 자체가 방대하다면 `계획/상용_서비스_계획.md` 상위 계획 수준에서 대기능을 둘로 정식 분리한다.
- **대기능(상위 단위)의 과도한 분할 방지 (초안·계획 단계 필수 검토):**
  - "Step 수를 3~4개 이하로 맞추라"는 규칙을 준수하겠다고, 상위 대기능(Feature) 자체를 자잘하게 쪼개버리는 꼼수(가짜 대기능으로 쪼개서 각 1~2 step씩 만드는 행위)를 **엄격히 금지**한다.
  - 대기능은 **"독립적으로 완성된 사용자 가치(End-to-End User Journey)를 온전히 품는 단위"**여야 한다. 초안 작성 및 계획 수립 시 기능이 파편화되지 않았는지 반드시 검토한다.
- **Step 적정 크기(골디락스) 상·하한선:**
  - **상한선(과대 뭉텅이 금지선 — 하나라도 해당하면 Step 분할 필수):**
    - 신규/수정 파일 수 **7개 초과** (또는 핵심 로직 파일 5개 초과)
    - 예상 diff **600~700줄 초과**
    - 독립된 사용자 여정(동선)이 **2개 이상** 결합 시
  - **하한선(과소 세분화 금지선 — 하나라도 해당하면 인접 Step에 무조건 통합):**
    - **독립 검증 불가능성 (단편 분할 금지):** 브라우저에서 눈으로 보거나 단일 E2E로 통과를 증명할 수 없는 단편(화면에 안 붙는 빈 컴포넌트 1개, 단순 DTO 파일 1개, 단순 CSS 토큰 1개 등)은 단독 Step 분할 금지.
    - **명세 오버헤드 역전:** 주니어에게 줄 명세서 분량(150~200줄)이 실제 구현 코드량과 비슷하거나 더 긴 자잘한 작업은 단독 Step 금지.
    - 예상 diff **100~150줄 미만**인 작업은 인접 Step에 통합.
- **Step별 수행 방식 동적 배정 및 시니어 실행 노동 분리:**
  - 뭉텅이로는 고위험인 작업도 위 골디락스 기준으로 쪼개어 격리된 영역(스캐폴딩, 폼 등)은 주니어 구현으로 배정한다.
  - 시니어 직접 구현 Step이라도 단순 실행 노동(전체 테스트 실행·신규 PR 생성·CI 대기)은 4단계 주니어(Gemini)에게 인계하여 고가 토큰을 절약한다.

## 5. PR 리뷰와 CI 확인

1. **상시 점검:** PR 생성/갱신 후 `gh pr checks --watch` 대기 중, CI 종료 후, 최종 보고 직전에 리뷰 코멘트(본문·라인·일반 코멘트)를 필수 조회한다.
2. **타당성 판단:** 코멘트 지적이 타당하면 즉시 수정하고, 사실과 다르거나 프로젝트 규칙과 충돌하면 근거를 밝혀 유지한다. 판단 근거는 진행 파일 또는 결과 파일에 기록한다.
3. **재검증:** 코드 수정 후에는 최신 커밋에 대해 다시 CI 종료를 확인한다.
4. **권한 경계:**
   - 주니어: CI 실패 및 명세 범위 내 명백한 코드 결함 수정 커밋·push 가능. 승인 밖 계약 변경은 정지 후 질문.
   - 시니어: 승인 범위 내 직접 수정·테스트 커밋 가능. 승인 밖 계약 변경은 사용자 결정 필요.

## 6. 완료 보고 및 세션 시작 멘트

1. **완료 보고 표준 문구:**
   구현부터 PR 검증까지 마치면 다음 형식으로 보고한다:
   “현재 <작업> 작업은 구현부터 PR 검증까지 완료되었습니다. PR #<N> 머지 후 아래의 다음 작업 단계 시작을 위한 세션 멘트를 활용하세요.”
2. **다음 세션 시작 코드 블록:**
   다음 작업이 남아 있으면 실제 머지 확인과 main 안전 동기화를 선행 조건으로 하고 완료한 작업을 반복시키지 않는 복사 가능한 코드 블록을 제공한다 (`[필수 가드레일]` 및 권장 Effort 포함).
3. **다음 작업 부재 시:**
   사용자 머지 대기와 “다음 작업 없음”을 명시한다.
