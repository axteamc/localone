## 0. 결론

1. **지금 공통 계약을 정하고 개발을 이어 갈 수 있다.** 다만 정할 수 있는 것은 원칙·범위·기술 결정·공통 규격까지다. 데이터 계약과 API 계약은 한 건도 없어서(`../team/contracts/` 폴더가 아직 없다) 기능별로 하나씩 만들면서 기준선에 더해야 한다.
2. **새 도구는 필요 없다. 이미 있는 운영 체계의 빈틈 여섯 개를 메우면 된다.** 문서별 단일 원본 표, 명세서·계약서·검증서 템플릿, PR 3자 대조 리뷰, 추적표, 변경 이력, 미결 질문 기록, `CI ok`와 `main` 보호가 이미 돌고 있다. 빠진 것은 ① 기준선 선언 ② 문서 상태 표기 통일 ③ 계약서의 태스크 머리말 ④ PR 템플릿 ⑤ 링크·ID 기계 검사 ⑥ 낡은 서술 정정이다.
3. **추천은 2단계다.** 1단계(11/13~11/16, D 약 0.3일)는 문서와 템플릿만으로 ①~④·⑥을 끝낸다. 2단계(⑤ 기계 검사, 약 0.3일)는 첫 계약서와 첫 구현 PR이 한 번 돈 뒤에 넣을지 정한다. OpenAPI·ERD 자동 산출은 11/19 1차 시연 뒤에 판단한다.
4. **가장 큰 위험은 도구가 아니라 D의 시간이다.** [일정 및 도달 점검 §6-3](일정_및_도달점검.md)에서 D는 이미 6.9일 필요·6일 가용으로 "위험"이다. 그래서 요구사항의 Must는 계약서 작성을 늦추지 않는 것만 골랐다.
5. **D의 결정이 필요한 것은 네 가지다**(§8). 그중 "02·04·계획의 '사용자 검토 전' 표기를 M1 범위에서 어떻게 승인할지"가 기준선 선언을 막는다.

### 3-3. 권위 순서와 충돌 처리

위가 아래를 이긴다. 다만 **충돌을 발견한 AI는 스스로 한쪽을 고르지 않는다.**

1. 사용자 원문과 00 §2 우선순위
2. 사용자 결정 기록: 스펙 변경 이력에서 "결정: 사용자"인 행. 같은 대상이면 번호가 큰 것이 이긴다(예: 알림함은 C-11이 아니라 C-47)
3. 승인된 제품 스펙: 02 + 상세 결정(둘이 다르면 C-46 상세 결정 — `기능_배정.md` "읽는 순서" ④의 기존 규칙)
4. 승인(머지)된 기능 명세서
5. 계약서(데이터·API·태스크)
6. 구현 코드와 테스트
7. 회고·제안·다른 AI의 응답

충돌을 찾았을 때 할 일:

- 구현이 계약과 다르면 계약대로 고친다(기존 10절 표). 계약이 명세서와 달라 **기능이 성립하지 않을 때만** `to:D`.
- 3번 이상의 문서끼리 다르면(예: X4) 고치지 않고 `검토 메모`에 `[기준 충돌] 무엇 — 어느 문서:줄과 어느 문서:줄 — 그동안 따른 쪽`을 적고, 위 순서에서 위쪽을 따라 계속한다. D는 PR에서 한꺼번에 본다.
- 안전한 진행 범위: 충돌한 지점에 닿지 않는 파트는 그대로 진행하고, 닿는 파트는 가짜 값 + `TODO(연결)` 또는 `TODO(기준)`으로 둔다.

핵심 규칙 하나: **파일이 `main`에 있다는 것과 승인됐다는 것은 다르다.** `specs/`와 `contracts/`는 머지 = 승인이라는 기존 규칙이 있다. `개발산출물/`·`계획/`의 제품 문서는 머지돼 있어도 머리말이 "검토 전"이면 초안이다(X3). 이 문서들은 기준선 문서에 실릴 때 승인으로 본다.

### 3-5. 변경 흐름

기존 장치를 순서로 세운 것이다. 새로 더한 것은 "영향 칸"과 경량 경로뿐이다.

| 단계 | 하는 일 | 기록 | 누가 |
| --- | --- | --- | --- |
| 1. 요청 | 무엇을 왜 바꾸는지 한 줄 | 사용자 요청, `to:D` 이슈, 검토 메모 `[계약 보완 필요]`·`[정해진 것 이견]` | 누구나 |
| 2. 영향 확인 | 아래 여섯 칸 중 닿는 곳을 표시: 제품 스펙 / 기능 명세서 / 데이터 / API / 화면·분기 / 태스크(진행 중 파트) | 변경 이력 행의 "대상" 칸 | D의 Claude |
| 3. 승인 | 제품 동작·범위는 사용자, 계약·기술은 D | 변경 이력 "결정" 칸 | 사용자 / D |
| 4. 원본 갱신 | 단일 원본을 먼저 고치고 파생 문서를 같은 차례에 맞춘다(02를 고치면 `PROJECT.md`·`기능_배정.md`도) | C-번호 한 행, 기준선 문서의 버전 올림 | D |
| 5. 알림 | `notify_junior.sh <역할> 공지` | `[D→역할]` 이슈 | D의 Claude |
| 6. 구현·검증 갱신 | 영향받는 파트·테스트·verify 수정 | PR, 추적표 | 담당 |

**경량 경로**(승인 없이 D의 Claude가 처리하고 PR 본문에 한 줄): 오탈자, 깨진 링크, 줄 번호 근거 갱신, 상태 칸을 사실에 맞추기(X2·X7 같은 것), 파생 문서를 원본에 맞추기. 조건은 **동작·범위·필드·오류 코드·화면 문구가 하나도 바뀌지 않는 것**이다. 하나라도 바뀌면 정식 경로다.

## 4. 요구사항 명세 [제안]

ID 접두사는 요구 문서 §7의 예시를 따랐다. 기존 체계(요구사항 `AUTH-01`·`LIB-01` 등, Step `VISIT-1`, 변경 `C-nn`, 미결 `Q-nn`, 원문 `O-nn`, 수용 기준 `AC-*`, 설정 `SET-n`)와 겹치는 접두사가 없음을 확인했다. 이 ID는 **도구에 대한 요구사항**이고 02(제품 요구사항)에는 넣지 않는다. `CHANGE-`는 변경 이력의 `C-`와 다른 것이다.

| `CI ok`(서버 시험·타입 검사·웹 내보내기·iOS 빌드) | 기계 | 그 커밋에서 시험이 통과하고 빌드된다 | 계약 준수(계약서 §7의 시험이 들어 있을 때만 그 범위에서), 실제 서버·실기기 동작, 외부 제공자 연동 |
| (채택 시) OpenAPI 대조 | 기계 | 경로·필드 이름·타입이 계약서 표와 같다 | 권한·소유자 격리·오류 조건·화면 문구 |
| 3자 대조와 가드 역추적(pr-review B) | 사람 + Claude | 명세서 결정이 코드에 있고 가드를 지우면 시험이 실패한다 | 리뷰어가 보지 않은 경로 |
| 시안·화면 확인 | 사람(D, 주니어) | 본 화면이 결정과 같다 | 보지 않은 플랫폼(웹·Android·iOS는 따로 적는다) |
| 기준선 승인 | 사람(D) | D가 그 판을 계약으로 인정했다 | 내용의 정확성 |

기계 검사는 team 레포가 비공개라 CI에서 계약서를 읽을 수 없다 **[사실]**. 계약서 쪽 검사는 D의 PC에서 로컬로만 돈다. 이 제한은 기준선 문서에 적는다.

### 7-2. 성공 지표

모두 git·PR·이슈에서 뽑을 수 있는 것만 골랐다. 목표값은 첫 반복(11/16~11/18) 값을 본 뒤 정한다.

| 지표 | 세는 방법 | 무엇을 알려 주나 |
| --- | --- | --- |
| 계약 없는 구현 PR 수 | `feat/*` PR 중 본문에 태스크 ID·계약 절이 없는 것 | 관문이 지켜지는가(기대 0) |

## 9. 이 문서의 한계

- 일정 초안 원본("2차 프로젝트 SDD 개발 일정")은 보지 못했다. 그 날짜와 형식을 옮겼다고 밝힌 [일정 및 도달 점검](일정_및_도달점검.md)을 근거로 썼다. 원본에만 있는 단계 정의나 산출물 요구가 있으면 §6-1 표가 달라질 수 있다.
- 코드는 읽기만 했다. 서버 시험·앱 빌드를 이번에 실행하지 않았고, "통과"는 결과 문서와 `main`의 CI 기록에 의존한다.
- team 레포는 로컬 사본 `0f52201`을 읽었다. 원격과 같은지는 세션 시작 훅의 동기화에 의존했다.
- 기능 명세서 3건은 브랜치의 파일 목록과 PR 상태만 봤고 내용의 품질은 평가하지 않았다(pr-review의 일이다).
- 소요 시간은 전부 가정이다. 계약서·구현 PR이 한 번도 끝난 적이 없어 실측이 없다.
- 외부 라이브러리·제공자의 현재 조건(한도·약관·가격)은 확인하지 않았다. 해당 항목은 모두 기존 Q- 번호의 "대기"로 두었다.
