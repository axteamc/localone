# 상용 서비스 계획 — 동네한권 (localone)

> 순서·선행·검수 관문의 기준 문서. 제품 동작은 [요구사항 정의서](../개발산출물/02_요구사항_정의서.md), 실행·D2 결정은 [프로젝트 설정 진행](../개발산출물/진행_프로젝트_설정.md)에서 관리한다.
> 팀 작업 방식(기획 → 계약 → 구현)과 역할별 배정은 `../team/CLAUDE.md`·`../team/기능_배정.md`를 따른다. 이 계획을 바꾸면 `기능_배정.md`도 맞춘다.
> 2026-11-10 SET-1 기획 반영 초안, 2026-11-11 개정(도서관 방문·커뮤니티 중심으로 재배치, 반납 비서 단순화 — [C-10·C-11](../개발산출물/스펙_변경_이력.md)). 사용자 검토 전이며 구현 승인이 아니다.

## 1. 프로젝트 개요와 목표

- 서비스명(초안): **동네한권 (localone)**. 저장소는 `axteamc/localone`.
- **큰 틀:** 시각화된 지역 도서관을 앱에서 "방문"하는 느낌으로 쓰는 서비스다. 책 빌리는 일도 편리하게 돕지만, 핵심은 **도서관을 기반으로 한 지역 소규모 독서 커뮤니티**다.
- 핵심 가치: 지도에서 도서관을 골라 들어가면(방문) → 그 도서관의 독서 기록·지역 SNS(핀터레스트형 게시물)를 만나고 → 게시물의 책에서 대여 경로(우선)·구매로 이어지며 → 내가 쓴 기록을 템플릿으로 꾸며 다시 광장에 올리는 순환. 반납 비서는 이 순환을 돕는 가벼운 보조다("빌릴 예정" → "빌렸어요" → 타이머·알림 → "반납했어요").
- 앱 중심(React Native + Expo, D2-2 확정)이며 웹은 같은 코드의 부연 출력이다. 실행 뼈대(INIT)는 처음부터 앱 기준으로 만들고, MOBILE Feature는 설치·스토어·카메라 스캔을 맡는다.
- 기존 북마크 수집·태그·확장 프로그램 계획은 초기 템플릿이다. 새 도서관 서비스 요구로 대체하며 별도 북마크 제품은 만들지 않는다. README의 기존 설명은 이번 범위 밖으로 남아 있다.
- 성공 판정 초안: 사용자가 지도에서 도서관을 골라 방문하고, 이웃의 게시물을 훑다가 책을 찾아 도서관 소장 조회까지 이어가며, 자신의 게시물을 올린다. 빌린 책은 "빌렸어요"로 시작해 알림을 받고 "반납했어요"로 끝낸다. 정량 전환율·유지율·비용 목표는 파일럿 기준선 수집 후 확정한다.

## C-46 적용 순서·시안 관문(2026-11-12)

[상세 결정 F4](../개발산출물/명세/SNS_검색_프로필_상세결정.md)에 따라 기존 M1 피드·검색·메뉴 변경은 해당 기능 명세에 반영한다. 새 프로필 수집·북마크·모임은 별도 작업으로 일정·담당을 배정하며 기존 M1 전체를 재편하지 않는다. D3~D6/F3 화면은 실제 시안 제시·사용자 검토를 필수로 거친다. 모임은 회차별 약속·기록·후기·다음 모임 생성이며 알림함(홈·내 정보의 알림 아이콘, C-47)을 포함한다. 기존 아래의 ‘알림함 제외’는 사용자 결정(C-47)으로 대체된다(서버 푸시는 여전히 안 함). 불참 패널티는 누적 1회 3일·2회 7일·3회 30일·4회 참가 불가이고, 불참 판정 조건·회차 세기·적용 범위·댓글 패널티 기간·D1 구매 연결·팔로우 효과는 각 세부 명세에서 정하며 그 전에는 임의 구현하지 않는다.

**담당 미정 항목 배정안(2026-11-12, SET-3 완료 시점, 사용자 검토 완료):** M1에서 가장 가벼운 A가 M2의 READ와 C-46 신규 작업(내 정보 3탭·북마크·팔로우 모음)을 맡고, B는 LOCAL 이후 CLUB, C는 LIB→LOAN 이후 MOBILE-2, D는 MOBILE-1(iOS 서명)과 공통 부품(앱 안 알림 목록·하단 탭)을 맡는다. 기준: ① 선행 Feature 담당자가 이어서(READ←LOAN 연결은 계약서로, CLUB←LOCAL 모임 카드, MOBILE-2←LIB) ② M1 부하 균형(C가 LIB+LOAN 6 Step이라 가장 무겁다). M2 착수 때 부하를 보고 D가 조정할 수 있다.

AUTH·INIT·RELEASE는 여러 제품 여정의 공통 기반이며 이를 임의의 UI/DB/서버 Feature로 더 쪼개지 않는다. VISIT는 "도서관에 들어가는 경험"(지도→방문 화면), LOCAL은 "게시물 올리기·발견", READ는 비공개 기록 회고, LOAN은 대출 보조, CLUB은 모임이라는 별도 완료 가치를 가진다. 지도·바텀 시트·API는 각 여정 내부 구성이고 별도 Feature가 아니다(알림함은 만들지 않는다).

### Step 크기 점검과 착수 관문

- 10개 대기능 모두 예상 Step 2~4개, 최대 4개를 넘지 않는다(INIT 제외 시 VISIT·LOCAL이 4개).
- 각 Step은 화면 또는 하나의 E2E로 확인 가능한 사용자 행동 하나를 담는다. DTO·CSS·DB만의 별도 Step을 만들지 않는다. LOCAL-2(피드·상세·도서 연결·이어 읽기·공감)는 요구사항이 여러 개이므로 계약서에서 파트(PR)를 나눌 때 가장 먼저 규모를 확인한다.
- 기능 명세서(주니어)가 승인되면 D가 계약서에서 Step을 파트(PR 하나)로 나눈다. 파트 크기는 `../team/docs/문서_운영.md` §3(파일 ≤7개, 예상 변경 ≤600~700줄, 독립 확인 가능)을 따른다. 현재 소스가 없어 실제 규모는 미산정이다.
- 상한을 넘으면 우선 부가 기능을 대기로 돌리거나 인접 경계를 재조정한다. 여전히 넘으면 최대 4개 안에서 재설계하며, 독립 사용자 가치가 입증되지 않은 Feature 분할은 금지한다. 숫자만 충족한 상태로 구현을 승인하지 않는다.
- 화면 공통 디자인·접근성은 각 Step의 완료 조건으로 포함한다. 여러 화면 완성을 단일 UI Step으로 묶지 않는다.
- D는 소유권·늦은 응답·외부 I/O·오류 경계를 계약서로 정하고 공통 엔진(조회 엔진)·AUTH를 맡는다. 기능 내부 동작은 담당 주니어의 명세서로 정한다. 알림은 기기 예약 방식이라 D의 서버 알림 작업자는 필요 없다(C-11).

## 3. 마일스톤과 출시 관문

> **M1 동결(2026-11-11, 사용자)**: 아래 범위로 M1을 고정하고 주니어 기획·구현을 시작한다. 새 아이디어와 요구는 **M2 또는 §4 대기 목록으로만** 받고, M1 범위를 바꾸려면 사용자가 "동결 해제"를 명시한다.
> - M1에 들어가는 요구사항(29개): AUTH-01~03, USR-01~02, LIB-01~07, VISIT-01~02, LOCAL-01~06, LOAN-01~05, NFR-02~05(NFR-01은 전 단계).
> - M1 방문 페이지(VISIT-02)는 피드(LOCAL-02)만 만든다. 책장·방명록·모임·스탬프 카드·도서관 룩(VISIT-03~07)은 M2이며, 책장이 나중에 아래에 붙을 수 있게 레이아웃만 열어 둔다. 룩이 M2여도 색·곡률은 처음부터 토큰으로 쓴다(기본 룩 warm).
> - M2: VISIT-03~07, READ-01~02, LOCAL-07~08, CLUB-01~02. M3: MOBILE-01~02, RELEASE.
> - 시작 방식: 선행이 필요한 부분은 가짜 값으로 먼저 만든다(`../개발산출물/00_기획_원본.md` §6). 미결 질문은 해당 Step 명세 직전에 푼다(`../개발산출물/모호점_해소_기록.md` §3).

1. **M0 기반:** SET-0 완료 확인 → 이번 SET-1 기획 검토 → D2 선택 → SET-1 세부 명세 승인 → SET-2. 기획 초안만으로 스캐폴딩을 시작하지 않는다.
2. **M1 제한 파일럿(방문·광장·가벼운 반납 비서):** AUTH + LIB + VISIT-1·2 + LOCAL-1·2 + LOAN. 지도/서지 제공자의 데이터 범위·갱신 주기·사용 조건을 확인하고, 사용자 A↔B 격리(예약 알림 포함)와 "지도 → 도서관 방문 → 게시물 → 책 소장 조회", "빌릴 예정 → 빌렸어요 → 알림 → 반납" 여정을 검수한다. 게시물은 **초대한 파일럿 참여자에게만** 보인다. 신고·운영 숨김이 없으므로 공개 범위를 넓히지 않는다. RELEASE-1/2로 제한 운영한다. M1이 커서 내부 순서는 명세 단계에서 D가 조정한다.
